시스템 구조

핵심 기능

약속을 생성하고 조회하며, 참여자를 초대하고 초대 수락이나 거절, 참여 취소 상태와 참여 마감 시각, 도착 상태를 관리합니다. 참여 결과에 따라 벌금과 보상을 계산해 내부 잔액에 반영하고 정산 결과와 거래 내역을 조회할 수 있습니다. JWT 인증과 친구 요청 및 수락, 거절, 친구 목록 조회도 구현했습니다.

문제 해결

1. 참여 상태 변경과 정산의 충돌 방지

문제

참여 마감과 취소 기능을 구현하면서 정산 대상 조회와 금액 반영 사이에 참여 상태가 바뀌면 정산 기준이 달라질 수 있음을 확인했습니다. 잠금이 풀리기를 기다리는 동안에도 상태가 바뀔 수 있어, 대기 전에 읽은 참여 상태를 그대로 사용해서는 최신 변경을 반영할 수 없었습니다.

해결

정산 대상을 일관되게 유지하기 위해 참여 변경과 정산이 같은 약속 행에 PESSIMISTIC_WRITE 잠금을 걸도록 했습니다. 약속을 먼저 잠근 뒤 참여 행을 다시 잠금 조회해 대기 중 바뀐 상태까지 확인하고, 마감 이후나 정산 완료 후에는 변경을 차단했습니다. 정산 대상에는 수락한 참여자만 포함했습니다.

결과

참여 변경과 정산의 처리 순서를 통일하고 잠금 획득 후 최신 상태를 확인하도록 바꿨습니다. 마감 직전에는 변경을 허용하고 마감 정각부터는 차단하는지, 정산 완료 후 도착 상태 변경이 막히는지 검증했습니다. H2 JPA 테스트에서는 참여 상태와 마감 정보의 저장 결과, 첫 수락 이후 마감 변경 제한도 확인했습니다.

2. 동시 정산 충돌과 금액 누락을 해결하고 재시도 정상 처리

문제

약속별 잠금만으로는 여러 약속이 공유하는 계정의 갱신 순서를 통제할 수 없어, 동시 정산 실험 20회 모두 데드락이 발생했습니다. 계정을 잠그기 전에 읽은 잔액을 사용하면 다른 정산이 반영한 최신 잔액도 놓칠 수 있었습니다. 여기에 벌금을 나눈 뒤 남은 금액과 관리자 입금 기록이 누락되어 잔액과 거래 내역이 어긋났고, 완료된 정산을 다시 요청해도 409가 반환되어 응답 유실 후 재시도가 어려웠습니다.

해결

교차 대기를 피하려고 관리자 계정을 포함한 대상 계정을 사용자 ID 순서로 잠갔습니다. 잠금 획득 후 DB에서 현재 잔액을 읽어 정산하고, 배분하고 남은 금액은 관리자에게 적립했습니다. 잔액, 거래 내역, 확정 결과를 한 트랜잭션에 저장해 함께 반영되도록 했습니다. 이미 끝난 정산은 약속 ID로 확정 결과를 찾아 204를 반환하고 금액이나 거래를 다시 기록하지 않도록 했습니다.

결과

동시 정산 20회에서 데드락 실패가 20회에서 0회로 줄었고, 추가 10회에서도 잔액과 거래 기록이 일치했습니다. 1,000원을 3명에게 각 333원씩 지급하고 남은 1원을 관리자에게 적립해 전체 금액을 보존했습니다. k6 VU 10으로 재시도한 300건의 204 응답은 3건에서 300건으로 늘었으며 금액은 약속별로 한 번만 반영됐습니다. 일반 테스트 82개로 정산 동작과 오류 시 전체 롤백도 검증했습니다.

3. 약속 목록 N+1 개선으로 SQL 202회에서 2회로 감소

문제

수락한 약속이 10개일 때 SQL 22회, 50개일 때 102회, 100개일 때 202회가 실행돼 목록이 커질수록 조회 횟수도 늘었습니다. 참여 정보를 가져온 뒤 지연 로딩된 약속과 생성자에 접근할 때마다 개별 SQL이 실행되는 것이 원인이었습니다. 수락 상태를 애플리케이션에서 걸러 최초 DB 조회에는 필요한 조건과 연관 데이터가 반영되지 않은 상태였습니다.

해결

약속과 생성자를 처음부터 함께 가져오도록 fetch join을 적용하고, 수락 상태 조건도 DB 쿼리로 옮겼습니다. 약속이 10개, 50개, 100개일 때 SQL 횟수가 일정한지 확인하는 회귀 테스트를 추가했습니다. 같은 데이터로 k6 VU 1, 10, 30에서 개선 전후를 각각 세 차례 측정하고 응답 데이터도 검증했습니다.

결과

약속 100개를 조회할 때 SQL이 202회에서 2회로 약 99% 줄었고, 10개와 50개에서도 2회를 유지했습니다. VU 10에서 p95 응답 시간의 세 차례 측정 중앙값은 58.09ms에서 8.81ms로 84.8% 감소했습니다. 개선 전후 본 측정 82,405건에서는 HTTP 오류나 응답 데이터 불일치가 없었습니다.

시스템 구조

핵심 기능

채용공고는 직군별로 걸러 보거나 페이지를 이동하며 탐색하고, 공고 상세 정보도 확인할 수 있습니다. 자기소개서는 작성하고 조회하거나 수정, 삭제할 수 있으며 글자 수 표시와 새 초안 저장 및 복원 기능도 구현했습니다. 매칭 결과에서는 기업별 점수와 순위를 시각화하고 추천 공고로 연결했습니다.

사용자 경험 개선

1. 서버 페이지네이션으로 채용공고 조회 범위와 탐색 방식 개선

문제

모든 공고를 한 페이지에 불러와 로딩에 시간이 걸렸습니다. 목록이 길어 어디까지 확인했는지 알기 어렵다는 사용자 의견도 있어, 한 번에 가져오는 공고 수와 탐색 위치를 함께 개선할 필요가 있었습니다.

해결

서버 페이지네이션 API를 연동해 페이지당 최대 20건만 요청하도록 바꿨습니다. 화면과 API의 페이지 번호 기준을 맞추고 서버가 반환한 전체 페이지 수를 탐색 버튼에 반영했습니다. 현재 페이지를 강조하고 번호를 10개 단위로 표시했으며, 이전 버튼이나 다음 버튼으로 이동할 때 번호 구간도 함께 바뀌도록 했습니다.

결과

전체 공고를 한꺼번에 가져오던 방식에서 페이지당 최대 20건을 조회하는 방식으로 바뀌었습니다. 사용자는 현재 페이지와 이동 가능한 범위를 확인하며 목록을 탐색할 수 있습니다. 페이지 번호가 API 요청과 응답에 올바르게 반영되는지, 첫 페이지의 이전 버튼과 마지막 페이지의 다음 버튼이 비활성화되는지도 검증했습니다.

2. 자기소개서 초안 자동 저장과 복원으로 작성 내용 유실 방지

문제

새 자기소개서의 입력값을 화면 상태에만 보관해 저장 전에 새로고침하거나 이동하면 작성 내용이 사라졌습니다. 지연 저장만으로는 대기 시간 안에 화면을 떠날 때 마지막 입력이 누락될 수 있었습니다. 사용자별 초안을 구분하지 않거나 늦게 도착한 서버 응답을 처리하지 않으면 다른 사용자의 초안에도 영향을 줄 위험이 있었습니다.

해결

초안을 사용자별 브라우저 저장소에 보관하고 입력을 멈춘 뒤 0.8초가 지나면 저장하도록 했습니다. 저장 대기 중 새로고침하거나 화면을 이동할 때는 최신 입력을 즉시 저장합니다. 재방문 시에는 초안 복원과 삭제를 선택할 수 있고, 계정이 바뀌면 입력 상태를 초기화해 내용이 섞이지 않도록 했습니다. 서버 저장에 성공하면 초안을 삭제하고 실패하면 유지해 재시도할 수 있게 했으며, 저장 중 중복 제출과 화면 이탈 후 도착한 응답이 새 초안을 지우는 상황도 막았습니다.

결과

같은 브라우저에서 작성 화면을 다시 열면 제목과 내용, 희망 직군을 복원해 이어 쓸 수 있습니다. 저장 대기 중 화면을 떠나거나 서버 저장에 실패해도 마지막 입력과 초안을 유지합니다. 사용자별 초안 분리, 저장소 오류, 늦은 응답 처리는 Jest와 React Testing Library 테스트 11개로 검증했습니다.

3. 분석 대기 화면에 스피너를 추가해 대기 상태 안내

문제

분석 중에는 정적인 안내 문구만 보여 결과를 기다리는 상황인지 화면이 멈춘 것인지 구분하기 어렵다는 사용자 의견이 있었습니다.

해결

안내 문구 옆에 CSS 회전 애니메이션을 적용한 스피너를 추가해 대기 중임을 보여 주었습니다. 서버에서 매칭 결과를 받으면 결과 화면으로 전환되도록 했습니다.

결과

분석 결과를 기다리는 동안 스피너가 회전하고, 결과를 받으면 화면이 전환되는 동작을 확인했습니다.

시스템 구조

핵심 기능

도서 대여 게시글을 등록하고 목록과 상세 내용을 조회할 수 있으며, 제목 검색과 본인 게시글 조회 및 삭제도 지원합니다. 게시글에는 이미지를 첨부하고 댓글을 달 수 있고, 회원가입과 로그인 기능을 구현했습니다.

직접 개발한 서비스를 대상으로 Docker 이미지 구성, Kubernetes 배포 환경 구축, Jenkins 빌드 자동화, k6 부하 테스트 및 수동 Pod 확장 수행

배포 환경 구축

1. 프론트엔드 및 백엔드 컨테이너화와 Kubernetes 배포

구축 과정

서비스별 실행 환경을 따로 관리하기 위해 프론트엔드와 백엔드 저장소를 분리하고 각각 Dockerfile을 작성했습니다. 프론트엔드는 이미지 빌드 과정에서 React를 빌드한 뒤 serve로 제공하고, 백엔드는 빌드된 JAR을 Java 17 환경에서 실행합니다. 생성한 이미지를 클라우드 Kubernetes에 배포하면서 DB 연결, 외부 API 접근, 이미지 저장 위치를 배포 환경에 맞게 조정했습니다.

결과

프론트엔드와 백엔드 컨테이너를 클라우드 Kubernetes 환경에서 실행했고, 서비스별 실행 환경과 시작 명령은 Dockerfile로 관리했습니다.

2. GitHub Webhook과 Jenkins 연동 및 빌드 자동화

구축 과정

코드 변경이 빌드로 이어지도록 클라우드 서버에 Jenkins를 설치하고 GitHub 저장소의 Webhook을 연동했습니다. 저장소에 코드를 push하면 Jenkins 빌드가 자동으로 시작되는지 확인했습니다.

결과

GitHub에 push한 코드의 변경 감지부터 Jenkins 빌드 실행까지 자동화해 빌드를 수동으로 시작하던 과정을 대체했습니다.

3. k6 부하 테스트와 수동 Pod 확장

수행 과정

Kubernetes에 배포한 서비스에 k6로 HTTP 요청을 보내 부하 테스트를 수행했습니다. 테스트 중 Pod 수를 수동으로 늘려 실행 규모를 조정했고, Grafana 대시보드에서 배포 환경의 상태와 Pod 확장 과정을 관찰했습니다.

결과

배포된 서비스에 부하를 발생시키고 Pod를 수동으로 늘리면서 Kubernetes의 실행 규모 조정과 상태 모니터링을 경험했습니다.
